# PBS-MAP-21423-01
## Mapping Profile: Mobile Robot Fleet Messages (ISO 21423 and VDA 5050) over PBS

**Status:** Draft (proposed Optional Interoperability Profile; not part of any PBS release)
**Version:** 0.1
**Applies to:** Gateways that carry MQTT-based mobile robot interoperability messages across intermittent links
**Related:** PBS-ENV-01, PBS-PRIO-01, PBS-SVC-01, PBS-AUTH-01, PBS-SEC-B-01, PBS-MUX-01, PBS-ADDR-02, PBS-DTN-MAP-02, PBS-PROX-01

> **Review status.** This draft was written from the public descriptions of ISO 21423:2026 and from VDA 5050, on which ISO 21423 is reported to build. The ISO text itself has not been checked. Every row of Section 4 marked "to confirm" SHALL be verified against the published standard before this profile leaves Draft. Nothing in this profile claims conformance to ISO 21423.

---

## 1. Purpose

ISO 21423:2026 and VDA 5050 let mobile robots, fleet managers and building systems from different vendors exchange position, state, task and availability data. Both are built on MQTT and JSON, which assume a broker that is reachable.

Robots also work where it is not: yards, mines, farms, disaster sites, long corridors with dead zones, and facilities whose network has failed. This profile lets a pair of gateways carry the same messages inside PBS envelopes across a link that comes and goes, so that both sides keep speaking the standard interface unchanged.

The profile does not alter either standard and does not define robot behavior.

---

## 2. Architecture

```text
Robot or fleet manager          Site broker / fleet manager
  (MQTT client)                       (MQTT)
        |                               |
  Edge bridge  == PBS envelopes over == Site bridge
  (local broker)   intermittent links   (MQTT client)
        |          (PBS-PROX-01, BPv7)
   robot side                        site side
```

- The **edge bridge** runs a local broker (or attaches to the robot's client) so the robot always has something to publish to.
- The **site bridge** republishes arriving messages to the site broker and collects messages bound for the robot.
- Between the bridges, each MQTT message becomes one PBS envelope.

---

## 3. Envelope Construction

- **PBS-M21423-REQ-001:** A bridge SHALL create one envelope per MQTT message, with Timestamp set to the time the message was received from the local broker, and its own Source ID.
- **PBS-M21423-REQ-002:** The payload SHALL be a PBS-MUX-01 container with a Service Intent frame, one message frame (Section 3.1), and a PBS-ADDR-02 destination frame naming the peer bridge. Messages in the COMMAND class SHALL also carry Authority Context and a Security frame (PBS-SEC-B-01).
- **PBS-M21423-REQ-003:** The receiving bridge SHALL apply PBS-SVC-01 freshness validation (PBS-SVC-REQ-004) before republishing and SHALL NOT republish a message that has expired.

### 3.1 Message frame

The message frame uses the PBS-MUX-01 frame type from Section 4. Its value is:

| Field | Size | Content |
|---|---:|---|
| map_version | 1 | `0x01` |
| encoding | 1 | `0x00` JSON, verbatim UTF-8. `0x01` CBOR (RFC 8949), converted under Section 5. |
| qos_retain | 1 | Bits 1–0: MQTT QoS. Bit 2: retain flag. |
| topic_len | 1 | Length of topic |
| topic | variable | MQTT topic, UTF-8, as published |
| body | remainder | Message body in the stated encoding |

## 4. Message Classes

Topic names in the first column are those of VDA 5050. The ISO 21423 equivalents are to be confirmed.

| Message | Direction | MUX type | Data class | Priority | Delivery mode | TTL | max_age |
|---|---|---|---|---|---|---:|---:|
| `state` (position, speed, task progress, errors) | robot → site | `0x03` Status | STATE | NORMAL | LATEST_STATE | 60 s | 30 s |
| `visualization` (high-rate position) | robot → site | `0x01` Telemetry | TELEMETRY | LOW | LATEST_STATE | 10 s | 5 s |
| `connection` | generated (Section 6) | `0x03` Status | STATE | HIGH | LATEST_STATE | 0 | none |
| `factsheet` | robot → site | `0x03` Status | STATE | LOW | AT_LEAST_ONCE | 86400 s | none |
| `order` | site → robot | `0x02` Command | COMMAND | HIGH | EXACTLY_ONCE_TRANSACTION | site policy | site policy |
| `instantActions` | site → robot | `0x02` Command | COMMAND | HIGH | EXACTLY_ONCE_TRANSACTION | 30 s | 30 s |
| Building system request (lift, door) — to confirm | robot → site | `0x02` Command | COMMAND | HIGH | EXACTLY_ONCE_TRANSACTION | 30 s | 30 s |
| Building system status — to confirm | site → robot | `0x03` Status | STATE | NORMAL | LATEST_STATE | 60 s | 30 s |
| Alarm (for example fire) — to confirm | site → robot | `0x04` Event | ALERT | CRITICAL | AT_LEAST_ONCE | 0 | none |

Values are defaults; a deployment MAY change TTL and max_age and SHALL document what it uses.

- **PBS-M21423-REQ-010:** For LATEST_STATE messages, a bridge or relay holding an older message with the same Source ID and topic SHALL replace it with the newer one (PBS-SVC-01 Section 5).
- **PBS-M21423-REQ-011:** The transaction identity for EXACTLY_ONCE_TRANSACTION is the order or action identifier the message already carries. The receiving bridge SHALL NOT republish a message whose identifier it has already republished.
- **PBS-M21423-REQ-012:** An `order` TTL SHALL NOT be `0`. An order that never expires can arrive after the site has reassigned the work.

MQTT QoS 0, 1 and 2 on the local side are honored on the local side only. End-to-end delivery follows the delivery mode above.

---

## 5. Encoding

- **PBS-M21423-REQ-020:** Encoding `0x00` carries the JSON body byte for byte.
- **PBS-M21423-REQ-021:** Encoding `0x01` converts JSON to CBOR by the RFC 8949 Section 6.2 rules and back by Section 6.1. The result is the same JSON value, not necessarily the same bytes: member order and number formatting can differ. A bridge SHALL use `0x00` when any consumer depends on the exact bytes.

A later revision MAY register a field dictionary to shorten member names.

---

## 6. Connection State

A fleet manager must not mistake a stored-and-forwarded message for a live one, or silence for a healthy robot.

- **PBS-M21423-REQ-030:** The site bridge SHALL publish the robot's connection state on the robot's behalf. It SHALL report the robot as not connected when it has received nothing from the edge bridge for a configured interval, and SHALL restore the connected state only on receipt of a message that passes freshness validation.
- **PBS-M21423-REQ-031:** The site bridge SHOULD expose, in a deployment-defined way, the age of the last state it republished.

Whether ISO 21423 defines a state value for "reachable through an intermittent link" is to be confirmed. If not, proposing one to its maintainers is preferable to a private extension.

---

## 7. Safety

- **PBS-M21423-REQ-040:** Functions that protect people or equipment in real time, including emergency stop and collision avoidance, SHALL NOT depend on this profile. They remain on the robot and its local safety systems.
- **PBS-M21423-REQ-041:** A robot receiving an order through this profile applies the same validation it applies to an order received directly. This profile adds PBS-AUTH-01 and PBS-SEC-B-01 checks at the edge bridge; it removes none.

Traffic coordination that assumes current positions (shared aisles, intersections, lifts) degrades when positions are late. A site SHOULD treat a robot whose state is older than `max_age` as occupying its last reported zone until it reports again.

---

## 8. Relationship to BPv7

Where the bridges are also bundle nodes, envelopes are carried under PBS-DTN-MAP-02. Where they meet directly, they use PBS-PROX-01 sessions. The MQTT-facing behavior is the same in both cases.
